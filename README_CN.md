## 为什么需要多Agent？

单个 AI 写代码就像一个人单干——能跑，但有盲区。真实的软件团队靠的是：

- **不同人发现不同问题** — 写代码的人看不到自己的bug
- **独立审查** — 每一行代码都有第二个审视
- **分工协作** — 有人理需求，有人做架构，有人写代码，有人做测试
- **迭代打磨** — 好代码是改出来的，不是一次写出来的

这个技能把上面的协作模式映射为一条 **Agent 流水线**。每个 Agent 有不同的**视角**和**人设**——它们不只是执行任务，而是带着不同的思维方式来解决问题。

## 快速开始

**不需要记任何参数**，输入任务就能用：

```
/multi-agent-code "用Python写一个带用户认证的todo API"
```

技能会弹出一个配置界面：

```
╔══════════════════════════════════════════════════════════╗
║           Multi-Agent Code — 当前配置                     ║
╠══════════════════════════════════════════════════════════╣
║  1. 最大轮次:     5     (跑到5轮或触发停止条件时停)       ║
║  2. 可选角色:     无    (analyst / architect / tester)   ║
║  3. 审查时机:     每轮   (每轮 / 每N轮 / 最后)            ║
║  4. 停止条件:     critical (critical/high/medium时停)    ║
║  5. 修复尝试:     1次    (发现严重问题后给几次修复机会)    ║
║  6. 自动/手动:    自动   (修复失败后自动停还是问你)        ║
║  7. 编程语言:     (自动检测)                              ║
║  8. 输出目录:     . (当前项目)                           ║
║  9. 目标评分:     关闭   (达到X分建议达标，0=关闭)        ║
║ 10. 评分稳定性:   1轮    (连续N轮达标才标记稳定)           ║
║ 11. 评分权重:     balanced (balanced/security-first/      ║
║                          performance-first/自定义)        ║
║                                                          ║
║  回复"go"使用默认配置，或者告诉我你想改的参数              ║
╚══════════════════════════════════════════════════════════╝
```

回复 **"go"**，流水线就启动了：

1. **扫描项目结构** — 理解你的目录布局，找到 build/test 命令
2. **编码者(Generator)** — 在项目里直接写代码
3. **自动验证** — 运行 build/lint/test，失败就进入修复
4. **审查者** — 检查 bug、安全漏洞，给出多维度评分
5. **编码者(Critic)** — 修复审查和验证发现的问题
6. ...以此类推，直到质量达标或触发停止条件

> 💡 Agent 在你的项目里**原地工作**。代码直接写入 `src/`、`tests/`。唯一的隐藏目录是 `.pipeline/`。

## 五个角色

| 角色 | 必须？ | 干什么 | 什么时候用 |
|------|--------|--------|-----------|
| **Analyst** 需求分析师 | 可选 | 把模糊需求变成精确的、可测试的规格书，标注验收条件 | 需求复杂、模糊，需要先理清楚 |
| **Architect** 架构师 | 可选 | 设计模块划分、组件关系、数据模型、API 契约、技术选型 | 系统有多个模块、数据库、外部接口 |
| **Coder** 编码者 | ✅ 必须 | 写代码。每轮用不同的"人格"，在前人代码基础上接力改进 | 永远需要 |
| **Reviewer** 审查者 | ✅ 必须 | 系统化审查全部代码。每个发现都标注严重级别和修复建议 | 永远需要 |
| **Tester** 测试者 | 可选 | 写完整测试套件，覆盖正常路径、边界值、异常情况 | 需要测试覆盖 |

### 编码者人格轮换

这是这个技能最核心的设计：**每一轮的编码者不是同一个人**，而是带着不同视角上场：

| 轮次 | 人格 | 心态 | 关注点 |
|------|------|------|--------|
| **第1轮** | Generator 生成者 | "先让它跑起来" | 功能实现、合理假设、快速出活 |
| **第2轮** | Critic 批判者 | "我来找茬" | 安全漏洞、边界条件、异常处理、并发问题 |
| **第3轮** | Refiner 精炼者 | "打磨到精品" | 性能优化、设计模式、代码可读性、文档 |
| **第4轮+** | Critic/Refiner 交替 | 持续迭代 | 继续加固和打磨 |

## 参数说明

**所有参数都有默认值，你可以改任意一个。**

| 参数 | 默认值 | 说明 |
|------|--------|------|
| **最大轮次** | `5` | 最多跑几轮编码，可设置任意正整数 |
| **可选角色** | 无 | 启用哪些额外角色：`analyst`, `architect`, `tester`。coder 和 reviewer 始终启用 |
| **审查时机** | `per_round` | 什么时候审查：`per_round`（每轮）、`milestone:N`（每N轮）、`batch`（最后一次性审） |
| **停止条件** | `critical` | 审查发现什么级别的问题时触发停止：`critical`（安全漏洞/数据丢失）、`high`（功能错误）、`medium`（代码异味）、`never`（永不停止） |
| **修复尝试** | `1` | 触发停止条件后，给编码者几次修复机会。`0`=立即停，`3`=给三次机会 |
| **自动/手动** | 自动 | 修复机会用完后：自动停止还是停下来问你 |
| **编程语言** | 自动检测 | 从你的任务描述里推断 |
| **输出目录** | `.` (当前项目) | 代码生成位置。默认在当前项目内原地工作，像真人开发者一样。设为 `./output` 可用沙箱模式 |
| **上下文文件** | 无 | 要修改的现有文件 |
| **目标评分** | `0` (关闭) | 建议评分目标，只用于提示进展，不能覆盖真实验证 |
| **评分稳定性** | `1` | 连续N轮达到建议评分后标记分数稳定 |
| **评分权重** | `balanced` | 维度权重预设：`balanced`（均衡）、`security-first`（安全优先）、`performance-first`（性能优先），或自定义如 `security:3,performance:0.5` |

### 三种配置方式

**1. 交互式（默认）：** 输入任务 → 看到配置 → 回复"go"或改参数

**2. 命令行参数：**
```
/multi-agent-code --max-rounds 5 --roles architect --stop-on high "任务"
```

完整参数列表：

| 参数 | 示例 | 对应设置 |
|------|------|---------|
| `--max-rounds N` | `--max-rounds 8` | 最大轮次 |
| `--roles X,Y` | `--roles analyst,tester` | 可选角色 |
| `--review X` | `--review milestone:3` | 审查策略 |
| `--stop-on X` | `--stop-on high` | 停止条件 |
| `--fix-attempts N` | `--fix-attempts 3` | 修复尝试次数 |
| `--auto` / `--no-auto` | `--no-auto` | 自动/手动停止 |
| `--language X` | `--language Go` | 编程语言 |
| `--files X,Y` | `--files src/main.py` | 上下文文件 |
| `--output-dir X` | `--output-dir ./src` | 输出目录 |
| `--target-score X` | `--target-score 8.5` | 目标评分 |
| `--score-stability N` | `--score-stability 2` | 评分稳定轮次 |
| `--score-weights X` | `--score-weights security-first` | 评分权重预设 |
| `--defaults` | `--defaults` | 全部默认，跳过配置 |

**3. 自然语言：** 直接在任务描述里说
- `"用3轮迭代，加上架构师"` → max_rounds=3, 启用architect
- `"每2轮审查，high时停止，手动确认"` → milestone:2, stop_on=high, 手动模式
- `"用Go写，最后再审查"` → language=Go, review=batch
- `"评分达到8分时提醒"` → target_score=8.0
- `"安全优先的评分权重"` → score_weights=security-first

## 流水线停止逻辑

有四种情况会停止流水线，**哪个先发生就按哪个停**：

```
第1轮: Generator写代码 → 验证(build/lint/test) → 审查
       → 发现1个critical漏洞 → 进入修复期 → 继续

第2轮: Critic修复 → 验证全部通过 → 审查 → 0个critical/high
       → ✅ 质量达标！提前结束（不用跑满5轮）

--- 或者修复失败的场景 ---

第1轮: Generator写代码 → 验证失败(test挂了) → 审查发现critical
       → 强制Critic轮，修复期(fix_attempts=1) → 继续

第2轮: Critic修复 → 验证通过但critical还在
       → 修复机会用完 → ⚠️ 停止：严重问题修不好

--- 或者停滞的场景 ---

第1~2轮: 验证通过，审查减少3个问题
第3~4轮: 验证结果不变，审查问题没有减少
       → 🛑 连续2轮无改进，停止

--- 或者跑满的场景 ---

第1~5轮: 持续改进...
第5轮: 验证通过，审查剩2个medium
       → 🏁 到达最大轮次，停止
```

## 多维度代码评分体系 🎯

每个审查轮次，Reviewer 会从 **6 个独立维度** 对代码量化评分（每个维度 1-10 分），并计算加权综合得分：

| 维度 | 评估内容 | 示例 |
|------|---------|------|
| **安全性** | SQL注入、XSS、认证绕过、密钥泄露 | "参数化查询完整，但缺少CSRF保护" |
| **正确性** | 逻辑错误、并发问题、边界条件 | "核心逻辑正确，但并发场景有竞态条件" |
| **性能** | 算法复杂度、N+1查询、资源使用 | "查询有N+1问题，建议用JOIN优化" |
| **可维护性** | 可读性、DRY、设计模式、文档 | "代码清晰，但parse_date参数过多" |
| **健壮性** | 错误处理、输入验证、超时重试 | "外部调用缺少超时和重试机制" |
| **完整性** | 需求覆盖、验收标准、文档 | "所有P0需求已实现，P1缺2项" |

**综合得分 = Σ(维度得分 × 权重) / Σ(权重)**，默认所有权重为 1.0。

### 权重预设

不同项目场景用不同权重：

```
balanced:          所有维度 = 1.0  (默认，均衡)
security-first:    安全性 = 2.0    (安全关键系统)
performance-first: 性能 = 2.0      (高并发/低延迟系统)
```

自定义权重：`--score-weights security:3,performance:0.5`

### 分数趋势可视化

流水线结束时会展示完整的质量演变：

```
📈 质量评分趋势:

  R1: ██████░░░░ 6.2  Generator  安全:5 正确:7 性能:6
  R2: ████████░░ 7.8  Critic     安全:8 正确:8 性能:7
  R3: █████████░ 9.1  Refiner    安全:9 正确:9 性能:9

  起始: 6.2 → 最终: 9.1 → 提升: +2.9 (+47%)
```

### 建议评分目标

评分可以用于观察质量趋势：

```
/multi-agent-code --target-score 8.5 --score-stability 2 "写一个API"
```

→ 连续 2 轮综合得分 ≥ 8.5 时显示达标提示。真正完成仍要求构建和测试等验证通过、验收条件满足，并且没有未解决的 critical/high 问题。

## 审查策略对比

| 策略 | 怎么审查 | 适合场景 | Token消耗 |
|------|---------|---------|-----------|
| `per_round` 每轮 | 每轮编码后都审 | 安全关键代码，追求最高质量 | 最高 |
| `batch` 最后 | 全部编码完成一次性审 | 快速原型、简单脚本 | 最低 |
| `milestone:2` 每2轮 | 每2轮审一次 | 效率和质量平衡 | 中等 |

## Agent之间如何交接

每个编码者产出三样东西给下一轮：

1. **相关代码和本轮 diff** — 包括受影响调用链、接口和测试，避免大项目上下文溢出
2. **变更日志** — 改了什么、为什么改、做了哪些设计决策
3. **遗留问题** — 还有哪些疑虑、建议下一轮重点关注什么

下一位编码者看到的不只是代码，还有**前人的思考过程**。

```
你的任务
  │
  ▼
┌─────────────────────────────────────────┐
│ 第1轮 Generator                          │
│ 产出: auth.py, models.py                │
│ 变更: 实现了基础认证流程                  │
│ 疑虑: OAuth还没做，错误信息不友好         │
└─────────────────────────────────────────┘
  │  ↓ 相关代码和 diff + 变更日志 + 遗留问题
  ▼
┌─────────────────────────────────────────┐
│ 第2轮 Critic                             │
│ 看到: 上轮的所有代码和思考                 │
│ 发现: SQL注入风险、缺少限流               │
│ 修复: 参数化查询 + token bucket限流       │
│ 疑虑: 考虑加OAuth支持，但不在本轮范围     │
└─────────────────────────────────────────┘
  │  ↓
  ▼
 ...继续迭代...
```

## 输出结构

Agent 在你的**项目目录内原地工作**，不会创建隔离的 `output/` 目录：

```
你的项目/                           # ← Agent 在这里工作
├── src/                            # 项目代码
├── tests/                          # 测试代码
├── ...                             # 原有项目文件
└── .pipeline/                      # 流水线元数据
    ├── project.json                # 检测到的验证命令
    ├── project_tree.txt            # 项目结构快照
    ├── config.json                 # 参数快照
    └── tasks/
        └── <task-id>/
            ├── request.md
            ├── spec.md             # 启用分析师时
            ├── architecture.md     # 启用架构师时
            ├── baseline.json       # 用户原有修改信息
            ├── baseline.patch      # 用户原有 Git diff
            ├── state.json
            ├── validation.json
            ├── change_log.md
            ├── open_concerns.md
            └── reviews/
```

> 💡 **`.pipeline/` 是唯一的新目录。** 把它加到 `.gitignore` 里就行。所有流水线元数据都在这里，不会污染你的项目。

## 使用场景

### 日常功能开发（默认配置）
```
/multi-agent-code "实现用户注册接口"
```
→ Agent 在你的项目里直接写代码。默认5轮上限，每轮审查。质量门禁通过后自动提前结束。

### 生产级系统
```
/multi-agent-code --roles analyst,architect,tester --stop-on high --max-rounds 15 "做一个多租户任务管理系统"
```
→ 5个角色全上，high级别问题就停，最多15轮打磨。

### 修改现有代码
```
/multi-agent-code "给认证模块加上OAuth2社交登录"
```
→ Agent 自动找到 `src/auth.py` 并在原地修改，不需要你手动指定文件。

### 建议评分目标
```
/multi-agent-code --target-score 8.5 "重构数据库层"
```
→ 连续达到 8.5 分时提示质量趋势；是否完成仍由真实验证和审查门禁决定。

### 沙箱模式（如需隔离）
```
/multi-agent-code --output-dir ./experiment "试试用 Rust 重写这个模块"
```
→ 不想污染项目时，代码生成到 `./experiment/`。

## 安装

本仓库同时提供两个入口：Claude Code 使用 `CLAUDE.md`，Codex 使用标准 `SKILL.md`。两者共享 `prompts/` 中的角色规则；Codex 版本还包含 `agents/openai.yaml` 界面元数据。

### 安装到 Codex

把整个 `multi-agent-code` 目录复制到 Codex 的 skills 目录，然后用下面的提示调用：

```text
使用 $multi-agent-code，在当前项目中实现这个需求，并通过多轮编码、审查和测试完成验证。
```

Skill 会优先使用宿主提供的真实子代理；如果当前产品不支持子代理，它会用同一模型依次执行隔离的角色阶段，并明确说明这是角色模拟。

### Markdown 与脚本分别做什么

- `SKILL.md` / `CLAUDE.md` 定义 AI 应遵循的工作流。
- `prompts/` 定义各角色的审查和编码规则。
- `scripts/pipeline_state.py` 确定性地生成任务 ID、保存 Git 基线、原子更新状态并校验恢复数据。
- 宿主产品负责真正的文件编辑、命令执行和子代理调用；本仓库不是独立运行的代码生成服务。

状态脚本仅依赖 Python 标准库。下面的模式当前会匹配 `scripts/test_pipeline_state.py`：

```bash
python -m unittest discover -s scripts -p "test_*.py" -v
```

### 三个可选辅助功能

**1. 需求文件（推荐）**

把完整需求写入 UTF-8 文件，可以保留多行格式，并避免需求内容出现在终端历史或进程参数中：

```bash
python scripts/pipeline_state.py init --project ./my-project --request-file ./task.md --max-rounds 8
```

`5` 只是默认轮数。`--max-rounds` 可以修改为任意正整数；也可以在调用 Skill 时直接说“最多运行 8 轮”。短且不敏感的需求仍可使用 `--request`。

**2. Dry run（预演）**

加入 `--dry-run` 后只输出计划生成的 task ID、目录和文件，不修改目标项目：

```bash
python scripts/pipeline_state.py init --project ./my-project --request-file ./task.md --max-rounds 8 --dry-run
```

确认结果后去掉 `--dry-run` 才会真正初始化。

## Critic 和 Reviewer 的区别

这是新手最容易混淆的地方：

| | Critic 批判者 | Reviewer 审查者 |
|------|-------------|-------------|
| **身份** | 编码者的一种人格 | 独立的审查角色 |
| **做什么** | 发现问题 **并修复** | 发现问题 **并报告** |
| **产出** | 修改后的代码 + 修复记录 | 审查报告（按严重度分级） |
| **类比** | 同事帮你改代码 | Code Review 审查意见 |

## 常见问题

**问：什么时候启用需求分析师？**
答：需求模糊或复杂的时候。分析师会把"做个登录"拆解成"支持邮箱+密码、OAuth2、记住我、密码重置、错误次数限制"这种精确的规格。简单明确的任务不需要。

**问：什么时候启用架构师？**
答：系统有多个模块、数据库、外部API调用的时候。架构师会设计好模块划分、数据模型、接口定义，编码者直接按图施工。单文件脚本不需要。

**问：为什么编码者有3个人格而不是1个？**
答：人看自己的代码有盲区。三个不同视角（快速出活→找茬修bug→打磨优化）覆盖了单一人格遗漏的问题。

**问：Token消耗大吗？**
答：每轮大约2-3次Agent调用（编码+审查）。默认配置（每轮审查）下跑3轮大约6-7次调用。质量和消耗是成正比的——想省Token就用 `batch` 审查策略。

**问：能中途中断再恢复吗？**
答：能。状态保存在 `.pipeline/tasks/<task-id>/state.json`。恢复前会校验任务结构和当前项目状态。

**问：支持哪些编程语言？**
答：全部。提示词是语言无关的。技能会从你的任务描述里自动检测语言，你也可以用 `--language` 明确指定。

**问：和直接用Claude写代码有什么区别？**
答：直接写是一次性的——你对输出不满意就只能手动改。多Agent流水线是迭代的——编碼者们在彼此的代码上接力改进，审查者在每一轮独立把关。最终质量通常比单次生成高得多。

## 已知限制

- **顺序执行** — 每个Agent等上一个完成才开始。不支持并行（因为后面的需要前面的产出）
- **文件系统状态** — 通过文件传递状态，保证了中断可恢复，但有 I/O 开销
- **模型质量依赖** — 技能提供结构和流程，代码质量取决于底层模型能力
- **没有人机协同编辑** — 你可以用 `--no-auto` 在每个关键点确认，但不能在中途直接改代码
