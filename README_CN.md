# Multi-Agent Code — 多Agent协作编码

> 让多个 AI Agent（需求分析师、架构师、编码者、审查者、测试者）像真实软件团队一样协作，通过接力迭代、独立审查和可配置的质量门禁，构建生产级代码。

## 为什么需要多Agent？

单个 AI 写代码就像一个人单干——能跑，但有盲区。真实的软件团队靠的是：

- **不同人发现不同问题** — 写代码的人看不到自己的bug
- **独立审查** — 每一行代码都有第二个审视
- **分工协作** — 有人理需求，有人做架构，有人写代码，有人做测试
- **迭代打磨** — 好代码是改出来的，不是一次写出来的

这个技能把上面的协作模式映射为一条 **Agent 流水线**。每个 Agent 有不同的**视角**和**人设**——它们不只是执行任务，而是带着不同的思维方式来解决问题。

## 快速开始

**不需要记任何参数**，输入任务就能用：

```
/multi-agent-code "用Python写一个带用户认证的todo API"
```

技能会弹出一个配置界面：

```
╔══════════════════════════════════════════════════════════╗
║           Multi-Agent Code — 当前配置                     ║
╠══════════════════════════════════════════════════════════╣
║  1. 最大轮次:     10    (跑到10轮或触发停止条件时停)      ║
║  2. 可选角色:     无    (analyst / architect / tester)   ║
║  3. 审查时机:     每轮   (每轮 / 每N轮 / 最后)            ║
║  4. 停止条件:     critical (critical/high/medium时停)    ║
║  5. 修复尝试:     1次    (发现严重问题后给几次修复机会)    ║
║  6. 自动/手动:    自动   (修复失败后自动停还是问你)        ║
║  7. 编程语言:     (自动检测)                              ║
║  8. 输出目录:     ./output                               ║
║                                                          ║
║  回复"go"使用默认配置，或者告诉我你想改的参数              ║
╚══════════════════════════════════════════════════════════╝
```

回复 **"go"**，流水线就启动了：

1. **编码者(Generator)** — 快速写出能跑的 todo API
2. **审查者** — 检查 bug、安全漏洞、边界条件
3. **编码者(Critic)** — 修复审查者发现的所有问题
4. **审查者** — 验证修复效果
5. ...以此类推，直到质量达标或触发停止条件

想跳过配置界面也可以用参数：

```
/multi-agent-code --defaults "写一个邮箱验证函数"
/multi-agent-code --max-rounds 5 --roles architect "用Go写一个CLI工具"
```

输出在 `./output/` 里，包含所有代码、变更日志和审查报告。

## 五个角色

| 角色 | 必须？ | 干什么 | 什么时候用 |
|------|--------|--------|-----------|
| **Analyst** 需求分析师 | 可选 | 把模糊需求变成精确的、可测试的规格书，标注验收条件 | 需求复杂、模糊，需要先理清楚 |
| **Architect** 架构师 | 可选 | 设计模块划分、组件关系、数据模型、API 契约、技术选型 | 系统有多个模块、数据库、外部接口 |
| **Coder** 编码者 | ✅ 必须 | 写代码。每轮用不同的"人格"，在前人代码基础上接力改进 | 永远需要 |
| **Reviewer** 审查者 | ✅ 必须 | 系统化审查全部代码。每个发现都标注严重级别和修复建议 | 永远需要 |
| **Tester** 测试者 | 可选 | 写完整测试套件，覆盖正常路径、边界值、异常情况 | 需要测试覆盖 |

### 编码者人格轮换

这是这个技能最核心的设计：**每一轮的编码者不是同一个人**，而是带着不同视角上场：

| 轮次 | 人格 | 心态 | 关注点 |
|------|------|------|--------|
| **第1轮** | Generator 生成者 | "先让它跑起来" | 功能实现、合理假设、快速出活 |
| **第2轮** | Critic 批判者 | "我来找茬" | 安全漏洞、边界条件、异常处理、并发问题 |
| **第3轮** | Refiner 精炼者 | "打磨到精品" | 性能优化、设计模式、代码可读性、文档 |
| **第4轮+** | Critic/Refiner 交替 | 持续迭代 | 继续加固和打磨 |

## 参数说明

**所有参数都有默认值，你可以改任意一个。**

| 参数 | 默认值 | 说明 |
|------|--------|------|
| **最大轮次** | `10` | 最多跑几轮编码。到最大轮次就停 |
| **可选角色** | 无 | 启用哪些额外角色：`analyst`, `architect`, `tester`。coder 和 reviewer 始终启用 |
| **审查时机** | `per_round` | 什么时候审查：`per_round`（每轮）、`milestone:N`（每N轮）、`batch`（最后一次性审） |
| **停止条件** | `critical` | 审查发现什么级别的问题时触发停止：`critical`（安全漏洞/数据丢失）、`high`（功能错误）、`medium`（代码异味）、`never`（永不停止） |
| **修复尝试** | `1` | 触发停止条件后，给编码者几次修复机会。`0`=立即停，`3`=给三次机会 |
| **自动/手动** | 自动 | 修复机会用完后：自动停止还是停下来问你 |
| **编程语言** | 自动检测 | 从你的任务描述里推断 |
| **输出目录** | `./output` | 代码和报告保存位置 |
| **上下文文件** | 无 | 要修改的现有文件 |

### 三种配置方式

**1. 交互式（默认）：** 输入任务 → 看到配置 → 回复"go"或改参数

**2. 命令行参数：**
```
/multi-agent-code --max-rounds 5 --roles architect --stop-on high "任务"
```

完整参数列表：

| 参数 | 示例 | 对应设置 |
|------|------|---------|
| `--max-rounds N` | `--max-rounds 8` | 最大轮次 |
| `--roles X,Y` | `--roles analyst,tester` | 可选角色 |
| `--review X` | `--review milestone:3` | 审查策略 |
| `--stop-on X` | `--stop-on high` | 停止条件 |
| `--fix-attempts N` | `--fix-attempts 3` | 修复尝试次数 |
| `--auto` / `--no-auto` | `--no-auto` | 自动/手动停止 |
| `--language X` | `--language Go` | 编程语言 |
| `--files X,Y` | `--files src/main.py` | 上下文文件 |
| `--output-dir X` | `--output-dir ./src` | 输出目录 |
| `--defaults` | `--defaults` | 全部默认，跳过配置 |

**3. 自然语言：** 直接在任务描述里说
- `"用3轮迭代，加上架构师"` → max_rounds=3, 启用architect
- `"每2轮审查，high时停止，手动确认"` → milestone:2, stop_on=high, 手动模式
- `"用Go写，最后再审查"` → language=Go, review=batch

## 流水线停止逻辑

有三种情况会停止流水线，**哪个先发生就按哪个停**：

```
第1轮: Generator写代码 → 审查 → 发现1个critical漏洞
       → 进入修复期，给Critic机会修 → 继续

第2轮: Critic修复 → 审查 → 0个问题
       → ✅ 质量达标！提前结束（不用跑满10轮）

--- 或者修复失败的场景 ---

第1轮: Generator写代码 → 审查 → 1个critical
       → 修复期(fix_attempts=1)，继续

第2轮: Critic修复 → 审查 → critical还在
       → 修复机会用完 → ⚠️ 停止：严重问题修不好

--- 或者一直没问题的场景 ---

第1~9轮: 写→审→没问题→继续...
第10轮: 写→审→2个low级别的小问题
       → 🏁 到达最大轮次，停止
```

## 审查策略对比

| 策略 | 怎么审查 | 适合场景 | Token消耗 |
|------|---------|---------|-----------|
| `per_round` 每轮 | 每轮编码后都审 | 安全关键代码，追求最高质量 | 最高 |
| `batch` 最后 | 全部编码完成一次性审 | 快速原型、简单脚本 | 最低 |
| `milestone:2` 每2轮 | 每2轮审一次 | 效率和质量平衡 | 中等 |

## Agent之间如何交接

每个编码者产出三样东西给下一轮：

1. **完整代码文件** — 不是 diff，是全量代码，下一位能看到完整的产品
2. **变更日志** — 改了什么、为什么改、做了哪些设计决策
3. **遗留问题** — 还有哪些疑虑、建议下一轮重点关注什么

下一位编码者看到的不只是代码，还有**前人的思考过程**。

```
你的任务
  │
  ▼
┌─────────────────────────────────────────┐
│ 第1轮 Generator                          │
│ 产出: auth.py, models.py                │
│ 变更: 实现了基础认证流程                  │
│ 疑虑: OAuth还没做，错误信息不友好         │
└─────────────────────────────────────────┘
  │  ↓ 完整代码 + 变更日志 + 遗留问题
  ▼
┌─────────────────────────────────────────┐
│ 第2轮 Critic                             │
│ 看到: 上轮的所有代码和思考                 │
│ 发现: SQL注入风险、缺少限流               │
│ 修复: 参数化查询 + token bucket限流       │
│ 疑虑: 考虑加OAuth支持，但不在本轮范围     │
└─────────────────────────────────────────┘
  │  ↓
  ▼
 ...继续迭代...
```

## 使用场景

### 快速原型
```
/multi-agent-code --max-rounds 1 --review batch "写一个PostgreSQL备份脚本"
```
→ 一个人写一次，审查一次，~2次Agent调用。

### 日常功能开发（默认配置）
```
/multi-agent-code "实现用户注册接口"
```
→ 10轮上限，每轮审查。质量达标自动提前结束。

### 生产级系统
```
/multi-agent-code --roles analyst,architect,tester --stop-on high --max-rounds 15 "做一个多租户任务管理系统"
```
→ 5个角色全上，high级别问题就停，最多15轮打磨。

### 修改现有代码
```
/multi-agent-code --files src/auth.py,src/models.py "给认证模块加上OAuth2社交登录"
```
→ Agent直接在现有文件上迭代修改。

## Critic 和 Reviewer 的区别

这是新手最容易混淆的地方：

| | Critic 批判者 | Reviewer 审查者 |
|------|-------------|-------------|
| **身份** | 编码者的一种人格 | 独立的审查角色 |
| **做什么** | 发现问题 **并修复** | 发现问题 **并报告** |
| **产出** | 修改后的代码 + 修复记录 | 审查报告（按严重度分级） |
| **类比** | 同事帮你改代码 | Code Review 审查意见 |

## 常见问题

**问：什么时候启用需求分析师？**
答：需求模糊或复杂的时候。分析师会把"做个登录"拆解成"支持邮箱+密码、OAuth2、记住我、密码重置、错误次数限制"这种精确的规格。简单明确的任务不需要。

**问：什么时候启用架构师？**
答：系统有多个模块、数据库、外部API调用的时候。架构师会设计好模块划分、数据模型、接口定义，编码者直接按图施工。单文件脚本不需要。

**问：为什么编码者有3个人格而不是1个？**
答：人看自己的代码有盲区。三个不同视角（快速出活→找茬修bug→打磨优化）覆盖了单一人格遗漏的问题。

**问：Token消耗大吗？**
答：每轮大约2-3次Agent调用（编码+审查）。默认配置（每轮审查）下跑3轮大约6-7次调用。质量和消耗是成正比的——想省Token就用 `batch` 审查策略。

**问：能中途中断再恢复吗？**
答：能。流水线状态保存在 `output/.pipeline/state.json`。下次启动时会检测到并问你要不要继续。

**问：支持哪些编程语言？**
答：全部。提示词是语言无关的。技能会从你的任务描述里自动检测语言，你也可以用 `--language` 明确指定。

**问：和直接用Claude写代码有什么区别？**
答：直接写是一次性的——你对输出不满意就只能手动改。多Agent流水线是迭代的——编碼者们在彼此的代码上接力改进，审查者在每一轮独立把关。最终质量通常比单次生成高得多。

## 已知限制

- **顺序执行** — 每个Agent等上一个完成才开始。不支持并行（因为后面的需要前面的产出）
- **文件系统状态** — 通过文件传递状态，保证了中断可恢复，但有 I/O 开销
- **模型质量依赖** — 技能提供结构和流程，代码质量取决于底层模型能力
- **没有人机协同编辑** — 你可以用 `--no-auto` 在每个关键点确认，但不能在中途直接改代码
